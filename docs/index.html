Overview

Why does the system believe this?

LexGraph is a governed semantic layer over both database tables and documents. Its single organising commitment is that every fact it holds carries a record of how it came to be believed — so that question always has a real answer, not a plausible one.

What it is

LexGraph sits between a firm's data and the people asking it questions. Underneath are two kinds of source: structured data (database tables reached through AWS Glue and Athena) and unstructured data (documents — filings, contracts, opinions, correspondence). On top is a knowledge graph of entities and the relationships between them, plus a set of approved metric definitions.

What makes it different from a search box or a chatbot over the same data is that nothing enters the graph anonymously. Each relationship — each edge — is an assertion: a claim recorded alongside how it was arrived at, what it rests on, how confident the system is, when it was learned, who has signed it off, and which firm it belongs to. There is exactly one function in the codebase that can create one, and it refuses to create an incomplete one.

The consequence is that a user can always ask a follow-up question that most systems cannot answer: where did that come from? For a fact read from a document, the answer is a file, a page, and the sentence itself. For a fact a rule worked out, the answer is a proof tree that unwinds to the documents and records at its base.

Who it is for

LexGraph is built as a whitelabel platform for legal AI products. Three audiences use it, and the documentation tries to serve all three:

Lawyers and analysts

Ask questions, read the answer, and check the citation. The pages worth reading are Asking questions, Provenance and the Glossary.

Administrators and risk

Set the trust thresholds, run the review queue, operate the ethical walls. See Governance settings, Reviewing claims and Tenancy and ethical walls.

Technical evaluators

Judge whether the guarantees are real. Start with The assertion contract, then How extraction works and Architecture.

The platform is domain-agnostic by construction. It reads a vocabulary pack that names the entities, relationships and rules of a domain; the legal pack is simply the default. A second pack for healthcare ships alongside it, not because healthcare is a target market but because a single-pack abstraction rots quietly and a second one makes the rot visible in a test rather than in a customer's deployment.

The value proposition, in one paragraph

In one paragraph

Any competent system can find a passage in a document and put a sentence in front of a lawyer. What a regulated buyer needs, and what nothing on the market reliably provides, is the ability to say which of its beliefs are mechanically checkable, which rest on a model's judgement, which were derived by a rule from other beliefs, and which are outright guesses — and to keep those categories apart at the moment a question is answered rather than in a report afterwards. LexGraph makes that distinction the primary key of its data model. A fact that a string search confirmed is on page 7 is a different kind of object from a model's view that one holding undercuts another, and the system will not let them be mistaken for each other. Everything else — the review queue, the ethical walls, the trust thresholds, the three-tier read path — follows from that one decision.

The five classes, at a glance

"Epistemic" means "to do with knowledge". That is the last time this documentation uses the word without a plainer one alongside. The epistemic class of a fact is how the system came to believe it, and it is one of five:

ClassHow it was reachedDoes a person sign it off?
DECLARED A system of record said so — a case management export, a scan of the data catalogue. No. It is true by definition of the source.
EXTRACTED_DET A quoted sentence was claimed to be on a named page, and a search of that page confirmed the words are there. No. The check is repeatable, so there is nothing for a person to add.
EXTRACTED_MODEL Something read into the document rather than merely found in it. Yes. This is the only class the review queue exists for.
INFERRED A rule derived it from other facts, which it names as its premises. Yes, and its proof tree can be opened.
PREDICTED A statistical guess from the shape of the graph. No document says it. Never used in an answer at all unless explicitly asked for.

Without this axis, a citation parsed out of a filing and a language model's opinion are both just edges in a graph, indistinguishable at the moment somebody asks a question. The assertion contract covers all five in full, along with the five invariants the system enforces and why review state is derived rather than chosen.

How a question is answered

Questions are resolved by trying three routes in order, most precise first, and the route that succeeded is reported back as part of the answer. That is not an implementation detail leaking out: "this came from an approved metric" and "similarity search chose which passages to read" are different claims about how much the answer can be trusted, and the person reading it is entitled to know which one they have.

1

Governed metric

A metric definition matched the question and compiled to SQL. No model was involved in producing the query.

The same question returns the same SQL every time.

2

Graph traversal

The answer came from walking assertions that clear the trust threshold and that this user is allowed to see.

Every fact in the answer is a cited assertion you can open.

3

Hybrid

Relevant passages were retrieved by similarity, expanded along verified relationships out from them, and the data catalogue supplied the definitions of any tables the question named.

Sources are cited; the expansion only follows trusted edges; the catalogue returns column definitions and never rows.

Asking questions explains what each tier means for trust, and the kill switch that governs model-written SQL.

What is not built yet

This documentation describes a system in active development, and it is more useful to be honest about the gaps than to describe an intention as a feature. The significant ones:

Honest gaps
  • Tier 1 returns SQL but not a result. The Athena executor is written and tested, including the firewall check inside it, but nothing connects it to the metric path, so a governed metric compiles to SQL that is never run. This is now the largest gap.
  • Nothing writes SQL from a question. Where no approved metric matches, no query is generated at all: tier 3 answers from passages, the graph and table definitions. A generator belongs inside tier 3, which already holds the catalogue it would need, and is not built. The query firewall that would check its output does exist and is tested.
  • One task only. Live ingest progress arrives over a WebSocket served by a single process, and ingestion itself runs as a background task inside the API container, so it dies with the container. The durable job store makes a failed run retryable, not resumable. The 30-second poll, not the socket, is the correctness guarantee.
  • The refused-question backlog is not durable. Deliberately: it is a list to read, capped per tenant, and the audit record is the log line rather than this. It empties on a deploy.
  • Nothing has been through a load test. The reasoner joins in Python over a tenant’s live facts, which is fine for thousands and unexamined beyond that. The interface does not change when that has to move into the database, but the timing will.

Four gaps that were on this list have been closed, and the order mattered: an inference over facts that do not survive a restart would produce a proof tree pointing at premises that no longer exist.

  • Assertions persist. They are written to Neptune as the hybrid reification below describes, so an approval survives a deploy. This was the largest gap.
  • The rules fire. One generic engine reads the when/then patterns from whichever pack a tenant runs, so the legal conflict check and the healthcare contraindication alert are the same code path over different data. Conclusions are staged for review rather than published, and carry their premises.
  • Vectors go to OpenSearch, with the matter wall applied as a pre-filter inside the k-NN query rather than afterwards.
  • Governance settings persist to DynamoDB, which matters most for the ungoverned-query kill switch: losing that on a deploy meant a firm believing questions were being refused while they were quietly being answered.

Deployment is no longer among them: all six stacks — LexGraphNetwork, LexGraphData, LexGraphAuth, LexGraphApp, LexGraphMcp and LexGraphWeb — are applied to a real account, and the document pipeline runs there end to end: a presigned browser upload lands in S3, a notification starts ingestion, and pages are transcribed, chunked, embedded and read by a model.

Where a page describes something in this list, it says so at that point rather than leaving the reader to check here.

A note on these documents

This site explains why the system is shaped the way it is, not only what it does. Several of the most instructive entries record a decision that was reversed: the character offsets that were demoted, the pattern-matching extractor that was deleted outright, the structural tenant isolation that turned out not to exist in the database being used. In each case the reversal is more useful than the conclusion, because the reasoning that led into the mistake is easy to repeat.

The documentation is written to agree with the code, and where the two disagreed while this was being written, the code won and the difference is noted. It reuses the application's own plain-language wording wherever the application has any, so the tooltip a user sees in the product and the explanation here do not drift apart.
