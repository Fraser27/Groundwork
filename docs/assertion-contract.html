The assertion contract

Every relationship in the graph is an assertion, and there is one function that can create one. That is what makes the guarantees on this page hold for the whole system rather than for the code paths somebody remembered to check.

src/graph/assertions.py

What an assertion is

A knowledge graph is entities joined by relationships. "Counsel Smith represents Acme Corp" is a relationship between two entities. In most systems that is the whole of it: a line connecting two dots, perhaps with a confidence number attached.

In LexGraph the same relationship is an assertion, and it carries:

FieldWhat it records
tenant_idWhich firm this belongs to. Never optional.
subject, predicate, objectThe claim itself: who, what relationship, to whom.
epistemic_classHow the system came to believe it. One of five; see below.
methodThe specific, versioned thing that produced it — a named model, a rule with its version, a catalogue scan.
confidenceA number from 0 to 1 for this one fact.
source_locatorWhere it came from, precisely enough to check by hand. For a document: the file, the page, and the quoted sentence.
premisesFor a derived fact, the facts it was derived from. Unwinds into a proof tree.
rule_id, rule_versionWhich rule derived it, if a rule did.
valid_from, valid_untilWorld time — the period during which the fact was actually true.
recorded_at, superseded_atTransaction time — when the system learned it, and when it stopped believing it.
review_stateWhether a person has signed it off. Derived, not chosen — see below.
matter_idWhich matter it belongs to, if any. This is what an ethical wall filters on.

Two clocks rather than one is worth pausing on. World time is when something was true; transaction time is when the system found out. Keeping both is what makes "what did the file show on the date we advised?" answerable — a real requirement in legal work, and one that is brutal to retrofit, because the information simply was not captured.

The identifier of an assertion is a hash of its own content, which has a useful consequence: re-ingesting the same document produces the same identifiers and therefore changes nothing. The method is part of that hash, so re-extracting with an improved extractor produces new assertions that supersede the old generation rather than colliding with it.

The five classes

This is the axis the whole design turns on. Without it, a citation parsed out of a filing and a language model's opinion are both simply edges, and there is no way to tell them apart at the moment somebody asks a question.

DECLARED

A system of record said so — a case management export, a scan of the data catalogue. Not inferred and not extracted from prose. If the source says it, it is true by definition of the source; if it is wrong, the source is wrong. Enters the graph without review.

EXTRACTED_DET

A claim that a deterministic check confirmed. Note carefully what this does and does not mean, because the name is misleading if you assume the obvious reading.

It does not mean "a regular expression found it". There is no pattern-matching layer in the system at all. What it means is: a model proposed that some text appears on some page, and a string search against that page either confirmed the words are there or it did not. The proposal is probabilistic. The confirmation is not, and the confirmation is what the class records.

Only presence claims can qualify, because presence is the only thing such a check can establish. "This quote appears on page 7" is verifiable. "This holding undercuts that argument" is not. How extraction works covers this in full — it is the most important idea in the system and the easiest to misread.

EXTRACTED_MODEL

A model's interpretation, which nothing can mechanically confirm. Everything semantic lands here: whether a citation was relied on or distinguished, whether one clause supersedes another, whether a party is adverse to another. This is the class the review queue exists for, and separating it from verified presence is what keeps that queue small enough to actually be read.

INFERRED

Derived by a rule from other assertions. It carries its premises — the facts it rests on — so it can always be explained as a proof tree, and so that retracting a premise retracts the conclusion.

Not built yet

No reasoning engine is wired up. The class, the premise structure, the proof-tree plumbing and the confidence ceiling below are all built and tested, and two rules are written out in the legal vocabulary pack (a conflict check and a stale-authority check). Nothing currently fires them, so in practice no inferred assertions exist.

PREDICTED

A statistical guess from the shape of the graph — the kind of suggestion a link-prediction model makes. Nobody asserted it and no document says it. It is a research hint, never a finding, and it is excluded from answers entirely unless a caller explicitly opts in to seeing suggestions. The exclusion is enforced in the scoping layer rather than left to each screen, and a caller who passes the class in explicitly still does not get it without the flag.

The five enforced invariants

These are checked by the single function that builds assertions. Each one is cheap to enforce at that boundary and expensive or impossible to bolt on later.

1. Attribution is mandatory

A tenant, a method, and a source locator are all required. An unattributed edge is not defensible, and a system whose purpose is to answer "why do you believe this?" cannot hold facts that have no answer. The method must be specific and versioned — llm:claude-sonnet-5, rule:conflict_check@v2, glue:catalog_scan — so that improving a producer supersedes its old output instead of silently mixing generations.

2. An inference must name its premises

A derived fact with no stated basis cannot be explained, and it cannot be retracted correctly either: nothing knows to withdraw it when the thing it rested on is withdrawn. So an inference with an empty premise list is refused. The reverse is also refused — premises on a fact that was not inferred are meaningless, and quietly accepting them would make the proof tree unreliable.

3. An inference is never more confident than its weakest premise

Without this rule, a chain of guesses can launder itself into a certainty: three facts at 0.6 combine into a conclusion at 0.95, and nothing in the record shows what happened. The build function refuses any inference whose confidence exceeds the minimum of its premises.

4. Governing relationships are validated against a closed list at write time

The failure this prevents is specific and worth stating concretely. An extractor records is_counsel_to. A conflict check queries REPRESENTS. Zero rows come back. The report reads as a clean conflict check, and it is not one — it is a query that missed a synonym. A write that fails loudly is enormously preferable to a query that silently returns nothing. See The predicate vocabulary.

5. Review state is derived from the class, never accepted from the caller

See below. This is the invariant most worth understanding.

A sixth rule, enforced elsewhere

Retracting a fact must transitively retract every conclusion that rested on it. That cannot live with the other five because they each inspect one candidate assertion in isolation, whereas this one has to walk the graph of premises. It lives in the retraction module instead. Nothing is ever deleted: a retraction marks the fact superseded from a moment in time, so a reading of the graph as it stood before that moment still shows the fact and still shows the conclusion it supported. That is what transaction time is for.

Why it matters more than it looks: the failure is silent. Retract the extraction that said counsel represents a party, leave the conflict flag standing, and the graph now asserts a conflict whose stated basis has been withdrawn. Every "why do you believe this?" answer for that flag then cites a retracted premise — which is precisely the question the system exists to answer well.

Why review state is derived, not chosen

The obvious design is a field that each part of the pipeline sets: a citation parser writes AUTO_ASSERTED, a model extractor writes PENDING. It is also the design that fails, and it fails in the way that is hardest to detect.

If review state is an input, then every code path that creates an assertion is a code path that can opt out of review. Not maliciously — by a mistaken default, a copy-pasted call, a new ingest route written in a hurry, a well-intentioned bulk backfill. And the failure is invisible: the graph looks the same, answers look the same, and the only symptom is that some facts nobody approved are shaping results. A code review cannot catch it reliably, because the check is "did the author of this call site think about review?" and the answer is unknowable from the diff.

So review state is not a parameter. The function that builds an assertion computes it from the epistemic class and nothing else:

DECLARED         → AUTO_ASSERTED
EXTRACTED_DET    → AUTO_ASSERTED
EXTRACTED_MODEL  → PENDING
INFERRED         → PENDING
PREDICTED        → PENDING

The two auto-asserted classes are exactly the two that involve no unverified judgement. A catalogue is a system of record. A confirmed quote was confirmed. Neither has anything for a human signature to add, and asking for one would be theatre.

Everything else waits. Because the mapping is computed rather than supplied, "no ingest path can opt out of review" is a property of the type, not a convention the team maintains.

The application's own wording for this, shown to users as a tooltip, is worth quoting because it is the same claim in plainer words:

Whether a person has signed this off. Derived from how the fact was reached, not chosen: a fact declared by a system of record, or a quote the system confirmed is on the page, goes live directly. Anything a model read into a document, and anything inferred, waits for a person. No ingest path can opt out of review.

Two gates that are easily confused

There are two separate questions about a fact, and conflating them causes real confusion:

  1. Review state — has a human signed off on this claim? Derived from the class, as above.
  2. Staged or live — is this claim in the part of the graph that queries read? An auto-asserted citation is signed off the moment it is created, but it still has to be written.

Keeping them apart is what makes a bad extraction run harmless. Staging is a transaction boundary: a whole document's assertions land together or not at all, so a half-ingested filing never looks like a complete one. A document that failed halfway through extraction contributes nothing rather than contributing a misleading subset. And since the original file is held immutably, re-running costs a re-extraction and nothing else.

How this is stored, and why it is denormalised

A fact is written in two places at once:

(:Matter)-[:ADVERSE_TO {assertion_id, epistemic_class, confidence,
                        review_state, superseded_at, tenant_id,
                        matter_id}]->(:Party)

(:Assertion {assertion_id, method, source_locator, valid_from,
             recorded_at, reviewed_by, ...})-[:PREMISE]->(:Assertion)

The relationship itself carries only the small subset a filtered traversal needs, so "walk only the edges I trust" stays a single hop. The full provenance and the premise structure live on a separate node and are read only when somebody asks why.

This is deliberately not the textbook answer. Storing every fact purely as a node with relationships pointing at it — full reification — would make every read three times the hops. Storing everything on the relationship's own properties could not express a proof tree at all, because a relationship cannot point at another relationship. The cost of the hybrid is two writes per fact that have to stay consistent with each other, which is a real cost, accepted knowingly.

Not built yet

The writer that would perform those two writes does not exist. Assertions are currently held in an in-process store and are lost on restart, and the read path reads from that store rather than from the graph database. The schema, the indexes and the scoped-read mechanism are all in place. Note that the in-memory store maintains a reverse index from premise to conclusion, which the retraction cascade walks — whatever replaces it has to maintain the same thing, or cascading retraction breaks silently.
