How it works

Tenancy and ethical walls

Two firms' data sits in one database, separated by a filter. That is an uncomfortable sentence, and the honest version of it raised the stakes on one file until it was built to a standard that matches.

Two levels of isolation

A tenant is one firm. A matter is one engagement — a case, a transaction, an advisory instruction — inside a firm. Both are enforced as filters on every read, and they differ in exactly one respect: who is allowed to change them.

LevelSet byChanges
Tenant Fixed at authentication, read from the verified sign-in token. Never from a request parameter — a caller who could name their own tenant could widen their own access. Effectively never.
Matter The caller's authorisation grants: a list of matters they may see, and a list they may not. Weekly, as staffing changes.

The matter level changing weekly is why it must be policy rather than data layout. An ethical wall goes up when a lawyer is staffed onto a matter that conflicts with one they have been working on, and it has to take effect immediately. If isolation were a property of where data lived, raising a wall would be a data migration, and nobody raises a wall that takes a migration.

Why not a separate graph per matter?

Because conflict checking is, by definition, across matters — and the shared entity is the signal.

If Acme Corp appears in forty matters, that is one node with forty relationships attached. A query asking "does the firm both represent and oppose this company?" is a short walk around that node. Split the graph per matter and Acme Corp becomes forty unconnected nodes, the walk is impossible, and the conflict check has to be rebuilt as a search-and-compare across databases — which is the thing knowledge graphs are good at, given up for an isolation model that was not needed.

The correction: there is no structural isolation

An earlier version of this design claimed tenants were isolated structurally, each in its own named graph, and said so in the project's own README. It was wrong.

The reversal

Named graphs are a concept from RDF and SPARQL, a different family of graph technology. The graph database in use here — Neptune Database — holds one property graph per cluster, and the query language it speaks, openCypher, has no notion of a named graph at all. There was nothing to isolate structurally. The claim described a feature of a different product.

So tenant and matter isolation are both property filters, differing only in who may change them. This was corrected in the code and in that module's own documentation rather than quietly patched, because the honest version raises the stakes on that one module: it is now the only thing standing between two firms' data, and it should be read knowing that.

A related option was examined and rejected. Neptune Analytics, a sibling product, does have discrete graph resources, so a graph per tenant is expressible there. But each one provisions a minimum of around 32 GB of capacity with no automatic scaling, which makes it a per-customer deployment shape rather than multi-tenant software. It also speaks only openCypher and has no full-text search. The considered conclusion is that a graph per tenant is affordable only if each tenant is a deployment, and that is a different business.

What that one module does about it

The design rule the scoping module exists to enforce is stated in the code as: it must be impossible to express an unscoped query. Not discouraged. Not reviewed for. Impossible. One forgotten tenant filter in one code path is a cross-firm privilege breach, and a privilege breach is not a bug that gets patched and moved past.

Three mechanisms, layered:

  • No part of the system outside the graph package writes a graph query by hand. Callers describe the shape of the traversal they want; the scoping module owns the filter clause. The metric compiler, for instance, reads a schema interface rather than the graph client, partly for this reason — and gained the side benefit that its tests need no database.
  • The client refuses to run a read that has not been scoped. A read must contain a placeholder token where the scoping clause belongs; a query without it is rejected before it reaches the database. Interpolating anything else is not offered.
  • There is no argument anywhere meaning "skip scoping". The narrow query object the scoping module returns can be narrowed further by a caller but has no operation that widens it.

Every scoped read composes five independent filters, each of which was a deliberate decision and so is named explicitly rather than buried in a query string:

  1. Tenant — the firm, from the verified token.
  2. Matter walls — the allowlist, then the denylist.
  3. Trust classes — which kinds of belief may inform an answer. Guesses are excluded here, and excluded a second time even if a caller passes them in explicitly.
  4. Confidence threshold — facts below the floor are visible in the review queue but do not shape answers.
  5. Time — by default only facts believed now; optionally, what was believed on a given date.

That last one is how "what did the file show when we advised?" is answered. Asking as of a past date returns facts that were believed then, including ones since retracted, because the question is about what was known at the time and not about what is true now.

Why a denial always beats a permission

A user's matter access is two lists: an allowlist of matters they may see, and a denylist of matters they may not. The denylist is applied after the allowlist and always wins.

The reason is that ethical walls and broad roles coexist, and they coexist in exactly the configuration where getting this wrong is worst. A senior partner has firm-wide access as a matter of role. That same partner is walled off from one matter because they previously acted for the other side. If a permission could satisfy a request that a wall forbids, then the broadest role in the firm defeats every wall in the firm — and the people with the broadest roles are precisely the people most likely to have a conflicting history.

So the wall wins. This mirrors the underlying authorisation language, where a forbid overrides any permit, and it means a wall cannot be defeated by also holding a broad role. The application says it to users this way:

An ethical wall. Matters you are walled off from are invisible to you: they do not appear in results, counts, or the graph. A denial always beats a permission, so a broad role cannot defeat a wall.

Why a walled matter answers 404 and not 403

This is a small technical decision with a large consequence, and it is the one most likely to look like a bug to somebody who has not been told.

When a user requests something they are not permitted to see, the conventional response is 403 Forbidden: this exists, and you may not have it. Groundwork returns 404 Not Found: there is no such thing here.

Why the conventional answer leaks

A 403 confirms existence. And confirming existence is exactly what an ethical wall is meant to prevent.

Consider a lawyer walled off from the firm's work for a company they used to act against. If probing a matter identifier returns 403, they learn the matter exists. Probe a list of plausible identifiers, or client names, and the 403 responses map out the firm's engagements — which is material non-public information about who the firm acts for, obtainable by a user who was specifically walled off from learning it. No document was read. The error codes were enough.

So the refusal is deliberately vague, and it is vague consistently. The scoping layer's own error message does not distinguish "walled off" from "does not exist". The review queue's lookup does not distinguish them. The document store's lookup does not distinguish them. The web layer maps every scope violation to 404 in one place rather than leaving each route to remember. A vagueness that holds in four places out of five is not vagueness; the fifth place is the whole answer.

The one thing a walled user is told

There is a tension here, and resolving it correctly is the most interesting part of the model.

Perfect vagueness would mean a walled user's results are silently narrower than they believe. And silent filtering is a more dangerous failure than the one the wall prevents. A lawyer who runs a conflict check and sees "no conflicts found" concludes there are no conflicts. If the truth was "no conflicts that you can see", the wall has caused precisely the harm it was built to prevent — the firm proceeds on a clean conflict report that was never clean.

The resolution is that the two questions are different questions:

  • "Does matter X exist?" — asked by probing a specific identifier. Refused without distinction. Answering it lets a user enumerate what they are walled off from.
  • "Is my view of this complete?" — asked implicitly by every user, all the time. Answered honestly with an aggregate: 3 matters withheld by an ethical wall. No names, no identifiers, nothing that narrows down which. Enough for the lawyer to know their result is partial and to escalate rather than rely on it.

A count is not a leak. Knowing that three matters are withheld tells a user nothing about which three, and it prevents them drawing a false conclusion from an incomplete answer.

Known gap to close

The interface currently derives that count on the client side from a flag on each matter, which would require the server to send walled matter objects to a user who may not see them — precisely what the model forbids. The endpoint must return visible matters plus a withheld count, never the walled objects even flagged as such. This is recorded as a required change in the project's own API contract; it is not yet made.

Automated callers have no identity of their own

Groundwork exposes its capabilities to AI agents as tools. Those tools carry no service identity and no standalone credentials. Every call carries the acting user's delegated token and is authorised as that user, with that user's walls.

This is non-negotiable where privilege is involved. An agent with its own broad credentials is a path around every ethical wall in the firm, and it is a path that leaves no trace of whose question it was answering. The tool surface runs the same code as the web interface — the same scoping module, the same vocabulary gate — for a related reason: a tool that answered a question differently from the equivalent web request would mean two implementations of governance, and the tool one is the one nobody audits.

The seam for physical separation

Some customers will eventually require their data to be physically separate rather than logically separated. The scoping module anticipates it with a single function that returns a storage key for a tenant. Today that key is used for naming resources — storage prefixes, search index names. If a contract ever requires a separate database cluster per firm, it becomes the cluster selector, and no calling code changes.

This is cheap to have now because every read already carries tenant identity through one place. It would be close to impossible to add later if those filters were scattered across hundreds of call sites, which is the argument for the discipline in the first place.
