Using it

Asking questions

A question is tried against four routes, most precise first. Which route answered is part of the answer, because "this came from an approved definition" and "a model wrote this query" are different claims about how much the number can be trusted.

The four tiers

Each route is attempted in turn and declines if it cannot answer. The first one that can, does, and reports itself.

1

Governed metric

An approved metric definition matched the question, and that definition compiled to SQL.

Trust: the highest available. No model wrote any part of the query. The same question produces the same SQL every time, so the same question produces the same answer.

2

Graph traversal

The answer came from walking assertions in the graph — only those above the confidence threshold, approved where approval was required, and visible to this user.

Trust: every fact in the answer is a cited assertion that can be opened to a page or a proof tree. A model may phrase the prose; it does not supply the facts.

3

Hybrid

Relevant passages are retrieved by similarity, then the graph is expanded outward from the documents they came from, following only trusted relationships.

Trust: sources are cited, and the expansion cannot pull in facts that fail the trust filters. Less precise than tier 2 because similarity search decides what to look at.

4

Generated SQL

No approved definition matched, so a model writes SQL against the real schema. It is checked against a query firewall before it runs.

Trust: not a governed answer. Treat it as a starting point, read the SQL, and check it before relying on the number. This is the only tier an administrator can switch off.

If all four decline, the answer says so plainly rather than producing something: no approved metric matched and nothing relevant was found in the graph. Rephrasing may help, or the question may need a metric definition that does not exist yet. An empty answer that admits it is empty is worth considerably more than a plausible one.

Why tier 2 is the differentiating one

Tier 1 is a good idea that other systems have. Tier 3, in isolation, is what most document AI does: find similar passages, hand them to a model, get prose back.

Tier 2 is different in kind. It expands along assertions rather than along similarity. A question like "which matters involve Acme Corporation" is answered by finding the Acme entity and walking the relationships attached to it — where every relationship walked has a class, a confidence, a method, and a page citation, and where relationships that fail the trust filters are not walked at all.

The practical difference shows up in what comes back with the answer. Every resolution carries a list of the assertions it used. That list is what makes the answer auditable rather than merely labelled: each identifier in it resolves to a document span or a proof tree. A retrieval system can tell you which passages it looked at. This can tell you which facts it relied on, and let you reject any one of them.

Matching in tier 2 is lexical — entity names and relationship names, not embeddings. That is deliberate rather than a shortcut: a question naming Acme Corporation should find the Acme entity by name, and doing it lexically means the result is reproducible and the reason for it is explainable. The system reports which terms matched, so the interface can explain why a fact was included. Semantics enter at tier 3, where they are labelled as such.

The kill switch

Tier 4 can be switched off per firm. When it is, a question that reaches it is refused rather than answered:

This question could not be answered from an approved metric or the knowledge graph, and ungoverned queries are switched off. An administrator can review blocked questions in Governance.

The reason only tier 4 has a switch is that it is the only tier where the system is guessing at intent rather than executing something a person approved. Tiers 1 through 3 execute definitions, traversals and retrievals that a human designed. Tier 4 asks a model to invent a query, and the model's understanding of the question is the only thing standing between the user and a wrong number that looks right.

Some firms will accept that trade for the coverage. Some will not, particularly during onboarding or in a regulated practice area. The switch makes that a policy choice rather than a product choice, and the application explains it to administrators this way:

Refuses any question that no approved governed metric can answer, rather than falling back to model-generated SQL. Governed metrics keep working. Refused questions are logged and make a good backlog of metrics worth defining.
The refusal log is a backlog

Refused questions are recorded — the firm, the user, the question, the reason, the time — and shown to administrators. This is not an audit trail for its own sake. A question people keep asking is a governed metric waiting to be written.

That reframes the switch from a restriction into a product feedback loop. Turn it on, watch what gets refused, and the list of definitions worth building writes itself in the users' own words.

The query firewall

When tier 4 does run, the SQL a model produces is checked before it is executed. The check parses the query into a syntax tree and walks it, extracting every table referenced anywhere — including inside joins, common table expressions, subqueries and unions — and validates them against what the caller may read.

Two properties are worth calling out, because a simpler check misses both:

  • It fails closed on a parse error. A query that cannot be understood is refused, not allowed through on the grounds that nothing suspicious was found.
  • It rejects anything that is not a single read. A comparable implementation checked only table names, which means DELETE FROM allowed_table would have passed — the table was allowed, and nothing looked at the verb. Non-read statements and multiple stacked statements are both refused.
Not built yet

Tier 4 has no SQL generator wired up, so in practice it always declines. The firewall exists and is tested; the model-backed generator that would feed it does not. The kill switch, however, is fully wired and does refuse — so a firm that turns it on gets the refusal and the audit entry today.

What makes a metric governed

A governed metric is a definition in a file that compiles to SQL deterministically. It is not a saved query and not a prompt. The fields that carry governance weight, rather than merely describing the number:

FieldWhat it governs
Time grains The only time buckets this metric may be reported in. Asking for a grain outside the list fails compilation rather than quietly answering at the wrong one.
Time grain column The single column those grains govern. Grouping by any other time-like column is refused as a bypass.
Additivity Whether the measure may be summed across periods. Fees billed may; a headcount may not, and summing it produces a number that means nothing.
Parameters The closed set of columns a caller may filter on.

Two of the compiler's governance rules are hard refusals rather than warnings: summing a semi-additive measure across a time grain, and slicing by time on a column the metric does not govern. Both produce a number that looks fine and is wrong, which is the category this system treats most severely.

A metric can also be compiled without being executed. That is not a debugging convenience — it is the point of a governed metric. A reviewer can read exactly what a definition will do before approving it.

Not built yet

No query executor is connected, so tier 1 currently returns the compiled SQL with no result attached. Requesting the SQL without running it is the honest mode locally.

A composition bug worth recording

Metrics can be defined in terms of other metrics. Doing that naively caused a real, subtle error in the system this compiler was modelled on.

Comparing one month's billings to another month's time

A realisation rate is fees billed divided by the standard value of the time recorded. Two component metrics, combined.

The reference implementation joined the two components on their shared dimension names. But the two components measure time on different columns — billings are dated by invoice date, time entries by the date the work was done. There is no shared name to align on. The join produced a number, and the number compared one month's billings against a different month's recorded time.

Nothing errored. The rate was plausible. It was wrong in a way that would require somebody to reconcile it by hand to notice.

The fix is that every component buckets its time into a shared alias, so the two halves are explicitly aligned on the same period rather than implicitly on a name collision.

Composition is also limited to one level deep, on the grounds that a reviewer must be able to read the emitted SQL and follow it. A definition three levels deep compiles to something nobody will check, and an unchecked governed metric is a governed metric in name only.

What comes back with an answer

Every resolution carries:

  • the tier that answered, and whether it counts as governed
  • a plain-language explanation of what that tier means, written for a lawyer
  • the SQL, where SQL was involved, in full
  • citations — document, page — where documents were involved
  • the assertions used, each of which can be opened to its provenance
  • the tiers attempted, so a tier-3 answer visibly shows that tiers 1 and 2 declined
  • warnings, including the explicit one attached to every tier-4 answer

The tier list being visible matters more than it looks. A user who sees that the governed route was tried and declined knows something useful: the question is not one the firm has defined an approved answer for. That is a fact about the firm's own governance, surfaced for free by the answer.
