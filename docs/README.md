# LexGraph documentation

A static documentation site. No server, no build step required to read it, no framework
and no dependencies. Open `docs/index.html` in any browser — including directly from
disk over `file://` — and the navigation, search and theme toggle all work.

## Reading it

```bash
open docs/index.html
```

That is the whole instruction. If you would rather serve it, anything static works:

```bash
python3 -m http.server -d docs 8080
```

## Structure

```
docs/
  index.html               Overview — the entry page
  assertion-contract.html  The five classes, the five invariants, derived review state
  extraction.html          The single model path and the quote verifier
  provenance.html          File + page + quote; demoted offsets; presigned URLs
  tenancy.html             Isolation, ethical walls, why 404 and not 403
  predicates.html          Governing vs descriptive; grounding without a model
  asking-questions.html    The four resolution tiers and the kill switch
  review.html              The review queue and what approving means
  governance.html          Every setting, and the cap/floor invariant
  glossary.html            Every term in plain language
  architecture.html        The six stacks, the stores, local development

  assets/docs.css          Palette copied from ui/src/index.css
  assets/nav.js            Sidebar, theme toggle, per-page table of contents, prev/next
  search.js                Client-side search over the prebuilt index
  search-index.json        The index — readable and diffable
  search-index.js          The same index as a script tag, which is what the browser loads
  build-index.py           Regenerates both index files. Standard library only.
```

Every content page is a complete HTML file rather than a fragment loaded into a shell.
That is what makes the site work from `file://`: a shell that fetched fragments would
hit the same cross-origin restriction described below, and deep links would break.

The sidebar is rendered from the `PAGES` array in `assets/nav.js`, so it stays
consistent across all eleven pages without being copied into each one.

## Regenerating the search index

After editing any page's content, headings or title:

```bash
python3 docs/build-index.py
```

It prints what it indexed, so a page that stopped being picked up is visible:

```
indexed 11 pages, 80 sections, 20,035 words
wrote search-index.json and search-index.js
```

The script needs no packages. It uses `html.parser` from the standard library — a
documentation build that requires `pip install` is a documentation build that stops
working.

### Adding a page

Three edits, in this order:

1. Create the page. Copy the `<head>`, the `<aside id="sidebar">` and the two closing
   `<script>` tags from any existing page — those are what wire up the shell.
2. Add it to `PAGES` in `assets/nav.js` so it appears in the sidebar and in the
   prev/next chain.
3. Add its filename to `PAGES` in `build-index.py`, then run the script.

The list in `build-index.py` is explicit rather than a directory glob, so a stray HTML
file cannot silently enter the index and the order of equally-scoring results stays
stable.

### Giving a section an anchor

Search results link to the nearest `<h2>` that has an `id`. A section without one is
still indexed, but a hit inside it links to the top of the page instead of to the
section. Every `<h2>` in these pages carries an `id` for that reason, and the same ids
populate the per-page table of contents in the sidebar.

## Why the index is shipped twice

`search-index.json` is the readable copy. `search-index.js` is the one the browser
loads, and it contains exactly the same data assigned to a global.

The duplication is not an oversight. A page opened from `file://` is treated as an
opaque origin, so `fetch()` on a sibling JSON file fails the cross-origin check in
Chrome and Safari, and there is no header or flag a static site can set to allow it. A
`<script>` tag has no such restriction. Since the requirement is that the site works
offline from disk, the browser gets the `.js`; the `.json` exists because it is what a
human or another tool should read.

Both are generated by the same script from the same data, so they cannot drift.

## Search behaviour

Matching is substring first, then tokens, in descending order of confidence:

1. the query appears in a page title
2. the query appears in a section heading
3. the query appears in the body text
4. every token in the query appears somewhere on the page

No stemming and no fuzzy matching. A search for "ethical wall" should return the ethical
wall page; one that also returns four near-misses is less useful than one that returns
nothing.

Results are grouped by page, so one page matching in three places reads as one place to
look rather than three competing answers. Keyboard: `/` focuses the box, arrows move,
Enter opens, Escape closes.

## Theme

The palette in `assets/docs.css` is copied from `ui/src/index.css`, including the five
epistemic colours, so a reader who learns them here recognises them in the application.
If the application's palette changes, copy the two `:root` / `[data-theme="dark"]`
blocks across.

The theme follows the operating system preference on first visit and remembers a manual
choice after that. Every access to local storage is guarded, because it is unavailable
or throws in some `file://` contexts — a page that cannot remember the theme still
toggles it.

## Conventions

- Written for a smart lawyer or a technical evaluator, not for whoever wrote the code.
  Explain a term before relying on it.
- Explain **why**, not only what. Where a decision was reversed, say so and give the
  reason — the reversal is usually the most instructive part. Those are marked with a
  "The reversal" callout.
- Prefer a concrete example over an abstraction. The `CITES` bug on
  `extraction.html` is worth more than three paragraphs of theory.
- Where something is not built, say so at that point rather than leaving the reader to
  discover it. Those are marked with a "Not built yet" callout.
- Reuse the application's own plain-language wording, from `ui/src/epistemic.ts` and the
  `FIELD_HELP` text in `src/governance.py`, so the product and the documentation cannot
  disagree.
- If a documentation claim contradicts the code, the code wins.
