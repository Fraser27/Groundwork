How it works

How extraction works

Reading facts out of documents is where a system like this either earns its defensibility or quietly loses it. Groundwork has one extraction path — a language model — and splits its output not by who proposed a claim but by whether the claim can be checked.

src/documents/extractors/model.py

The shape of it

A document arrives, is converted to text with page numbers preserved, and is split into passages. Each passage goes to a language model once, with a system prompt that asks for two kinds of claim and insists on keeping them separate, because they are checked differently:

  1. Entities — something named in the passage: a party, a court, an authority, a date, a docket number. This is a claim about presence only. It is verified by searching the passage for the model's quote, so the quote must be copied exactly.
  2. Relationships — something the passage supports that no search could confirm: that one holding undercuts another, that a clause supersedes an earlier one, that a party is positioned against another. These go to a human reviewer.

Everything the model returns is then put through two gates before anything reaches the graph, both of them there because model output is untrusted input:

  • The relationship name must exist in the vocabulary, matched exactly. An invented name is dropped rather than quietly widening the schema. No model adjudicates whether two names mean the same thing — see The predicate vocabulary.
  • The quote must actually appear in the passage. A claim whose quote cannot be found is dropped entirely, not stored with a caveat.

The verifier

The check itself is unglamorous, which is the point. The model returns a quote; the code searches the passage text for it. An exact match is preferred. Failing that, the quote is matched allowing any run of whitespace where the quote has a space, because a document converter's line joins legitimately differ from how a model echoes a passage — a sentence broken across two lines in the PDF comes back to the model as one line, and refusing that would reject correct claims for a typesetting reason.

Anything beyond whitespace differences is paraphrase, and the claim is dropped. A quote a reader cannot find in the document is not provenance. The application says the same thing to users this way:

The words from the document, copied exactly. Not a summary: a paraphrase could not be searched for in the original, so a claim whose quote cannot be found on the stated page is refused rather than recorded.

When the check passes, both halves of what happened are recorded in the fact's method field:

llm:global.anthropic.claude-sonnet-5+verify:quote@v1

A model proposed it; the quote check confirmed it. The verifier carries its own version number, separate from the model's name, so that if quote matching ever changes the previous generation is superseded rather than mixed in with the new one.

Why EXTRACTED_DET means "a check confirmed it"

The class name EXTRACTED_DET reads as though it means "extracted deterministically", and in an earlier version of this system it did: a regular expression found a citation and the citation went into the graph. That extractor no longer exists. The class was redefined rather than retired, and the redefinition is the most important idea on this page.

The reversal

EXTRACTED_DET no longer means "a regex found it". It means a deterministic check confirmed it: a model proposes that some text appears on some page, and a string search against that page either agrees or does not. The proposal is probabilistic; the confirmation is not, and the confirmation is what the class records.

That keeps the class meaningful. It now means "a deterministic check confirmed this", rather than "a pattern matched something", and it lets the review queue hold only genuine judgement calls. No allowlist anywhere.

The value of this is that the split between "goes live immediately" and "waits for a person" no longer depends on who proposed the claim. It depends on whether the claim is checkable. A model is perfectly capable of producing a claim that a machine can verify, and when it does, a human signature adds nothing. Insisting on one would be theatre, and expensive theatre — see why the split exists at all.

Why only MENTIONS may be verified presence

A quote match establishes exactly one thing: that these words appear on this page. It establishes nothing about what they mean. So only relationships that claim presence and nothing more may carry the verified class. In the legal vocabulary that is a single relationship, MENTIONS, and the constraint is enforced by the assertion builder rather than left to the extractor's good behaviour.

Anything that implies significance stays a model interpretation and waits for review: CITES implies reliance, ADVERSE_TO implies a position, SUPERSEDES implies a legal effect. None of those is established by finding words on a page.

This constraint exists because of a specific, real bug in the earlier design.

The Brown v. Board example

The old citation parser auto-asserted CITES whenever it matched the shape of a case citation. So the sentence

The court declined to follow Brown.

was recorded in the graph as reliance on Brown — an edge asserting that this document cites that authority, entering the graph with no review, at high confidence, because a pattern had matched.

The parser could not read negation. It could not read hypotheticals ("had the plaintiff relied on Brown…"), or a string cite in a passage distinguishing the case, or a reference inside a block quote from the opposing brief. It matched shape, not meaning.

Now: the model reads the sentence and proposes something interpretive — that the document distinguishes Brown, say. Nothing can mechanically confirm that reading, so it is EXTRACTED_MODEL, capped below the trust threshold, and waits for a lawyer. Separately, the fact that the words "Brown" appear on that page can be confirmed by search, so a MENTIONS edge is verified and goes live. The document becomes findable immediately; the claim about reliance does not exist until a person agrees with it.

The distinction the example turns on is worth stating flatly: finding a name is not the same as recording what the name was doing there. The old design collapsed the two, and the consequence was a graph that asserted reliance that never existed — the exact kind of fact this system would then confidently defend, with a page citation, to somebody who trusted it.

Why there are no allowlists

The deleted extractor had real virtues. It ran in a third of a millisecond, made no network call, and produced byte-identical output across a hundred runs. Those are not small things, and they did not survive contact with the requirement. Three reasons, and the second is the subtle one:

Its offsets pointed into a buffer nobody can see

The character offsets it recorded indexed the document converter's reconstructed text buffer, not the PDF. No viewer can seek to them. There was a test proving the offsets were internally consistent, and it proved consistency with a buffer no user will ever open. Worse: re-parsing a document after a converter version change shifts every offset downstream, silently repointing stored assertions at the wrong text. See Provenance.

Its allowlists silently missed anything not enumerated

It carried a list of roughly forty-five reporter abbreviations and around twenty court name patterns. A court that nobody had thought to enumerate simply did not exist in the graph. No error, no warning, no gap visible anywhere — the document was processed successfully and the court was absent.

And then the failure compounded. A separate guard existed to stop the model from proposing relationships the deterministic parser was responsible for, on the sound reasoning that two producers competing for the same relationship would create duplicate and conflicting edges. Put the two rules together and a novel court could not be extracted by the parser and was blocked from being rescued by the model. Two individually defensible rules combining into a dead end, with silence as the symptom.

The judgement that resolved it

Maintaining allowlists is a cost that has to be paid forever, by somebody who knows which reporters and courts exist, and the failure mode of not paying it is invisible. A strong model is better at exactly the classification the pattern matcher got wrong. So the allowlists went, along with the extractor that needed them, and the prompt deliberately contains no list of known courts or reporters.

It auto-asserted a relationship implying reliance

Covered above. This was the one that made the decision easy.

Why the split exists at all

An obvious objection to all of this: if the model is untrusted, why does any of its output go live without review? Why not review everything it says?

Because a queue nobody can clear gets rubber-stamped, and a rubber-stamped queue destroys the guarantee it exists to provide.

A 300-page bundle produces hundreds of extracted claims. If every one needed a human decision, the queue for a single matter would be unclearable, and the predictable human response is to approve in bulk without reading. At that point the review state on every fact in the system is a lie: it says a person checked this, and no person checked it. The system would still print "approved by" on every edge, and the word would mean nothing.

So the split is on checkability, not on who proposed the claim. Claims a machine can confirm are confirmed by a machine. The queue holds only genuine judgement calls — the ones where a human actually has something to contribute — and stays small enough that reading it is realistic. Reviewing claims follows this through.

The confidence ceiling

One more guard, and it is independent of everything above. A model's self-reported confidence is not evidence, so it is capped: an interpretive claim can carry at most 0.79, whatever the model says about itself.

The retrieval trust threshold is 0.80.

The gap is deliberate and it is load-bearing. An unreviewed model interpretation sits below the threshold by construction, so it cannot shape an answer even if the review gate were bypassed entirely — by a bug, by a misconfigured route, by a future code path nobody has written yet. Two independent mechanisms have to fail before an unapproved interpretation reaches a user. The coupling is enforced in code rather than merely documented; see the cap/floor invariant.

A verified presence claim is set to 0.95 rather than 1.0, which is a small point worth making because it is honest. The search proved the words are there. It did not prove that the model normalised those words to the right entity — deciding that "Acme Corp." and the "Acme Corporation" already in the graph are the same company is still the model's work, and it can be wrong.

What else gets dropped, and why silently is fine

  • A relationship name that is not in the vocabulary. Logged and discarded. Accepting it would let a model widen the schema.
  • A quote that is not verbatim. Logged and discarded, whether the claim was presence or interpretation. Storing an interpretation with an unverifiable quote would produce a review-queue item a reviewer cannot check.
  • A claim whose subject and object are the same entity. Discarded — a self-referential edge is a normalisation artefact, not a fact.
  • Any claim that violates an assertion contract invariant. Logged and discarded, which is how the presence-predicate constraint is actually enforced: the extractor does not have to remember it, because the builder refuses.

A failure anywhere in a document aborts the whole extraction pass rather than staging a partial result. A document half-extracted must not look fully extracted, and the original bytes are still held, so re-running costs one re-extraction and nothing else.

Text is searchable before any of this is reviewed

Passages are indexed for search before the review gate, deliberately. Verbatim text is a quote, not a claim: putting the words of a document into a search index does not assert anything about what they mean. Lawyers expect to be able to search a document the moment it lands, and withholding that for hours while a queue is worked would make the product unusable.

The review gate protects the graph — the structured claims that shape answers — not the search index. A stricter posture is defensible and was considered; it was rejected as unusable rather than overlooked.
