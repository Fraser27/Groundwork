Architecture

Six infrastructure stacks split by how often they change and how much damage a bad deployment does, not by feature. A graph database, a vector search service, and a managed model service. Locally, a container that speaks the same graph language stands in for the managed one.

The data flow

One rule governs the whole picture: the uploaded file is the only source of truth, and everything else is a derived index that can be dropped and rebuilt.

upload   → object storage (immutable, versioned, encrypted) + a job record
         → Textract             (text and layout, with page numbers)
         → split into passages  (page numbers preserved — they become the citation)
         → model extraction     → confirmed presence  → live immediately
                                → interpretation      → review queue
         → embed passages       → vector search index
         → stage facts → human review → promote → rules (not built)

The consequence of that rule is that a bad extraction run is never a data-loss event. The evidence is untouched; discard the derived facts and run again. That is what made it possible to delete the pattern-matching extractor outright rather than living with it — see How extraction works.

Note where the search index sits relative to the review gate. Passages are indexed before review, deliberately: verbatim text is a quote, not a claim, and lawyers expect to search a document the moment it lands. The gate protects the graph, not the search index.

Structured sources are treated entirely differently. Their data never moves. Only metadata — tables, columns, metric definitions — enters the graph, and rows are queried in place at the moment a question is asked.

The six stacks

Split by deploy cadence and blast radius. The organising question is not "which feature does this belong to?" but "what happens when this is redeployed, and how often will that be?"

StackContentsWhy separate
network Virtual network, subnets, security groups, service endpoints, outbound gateway. Changes rarely, and everything depends on it.
data Graph database, vector search, the document and job stores. Holds the only irreplaceable state, and the graph cluster takes around fifteen minutes to create.
auth User directory and the authorisation policy store. Deleting a user directory is unrecoverable. It gets its own blast radius.
app The containerised API — control plane, serving, workers — behind a load balancer. Redeployed constantly. Keeping it separate means a routine release cannot touch the graph.
mcp The agent tool server, on a managed agent runtime. A different runtime with its own constraints, notably on which availability zones it supports.
web Content delivery network in front of the browser application. Static assets on a different release cadence from the API.

For comparison, the AWS reference implementation this borrows ideas from uses sixteen. What was dropped, and why, is recorded in the project's own decision log — mostly enterprise catalog governance that a per-firm tenancy model does not need, a SPARQL federation layer that suits a table-first system rather than a document-first one, and a code-generation toolchain whose build tax was real and whose benefit at this size was not.

The three stores

Graph database — Neptune Database

Holds the assertions. The choice of Database rather than the Analytics sibling is covered in Tenancy and ethical walls: Analytics has discrete graph resources, which would allow a graph per firm, but each carries a minimum capacity floor with no automatic scaling, making it a per-customer deployment shape rather than multi-tenant software.

The instance class deployed is the smallest burstable one — free-tier eligible for a fixed number of hours, and explicitly not production-grade. It is a context parameter rather than a constant, so raising it does not require a code change. It should be raised before any load test.

Two properties of this database shape the code more than they look:

  • There is no schema DDL. No uniqueness constraints, no explicit indexes — it indexes everything automatically. So every constraint the codebase defines is applied in local development and skipped in deployment. That is a real divergence, not a shim: a uniqueness constraint that catches a duplicate locally will not catch it when deployed, which is why uniqueness is enforced by content-addressed identifiers instead of by the database.
  • Authentication is by network identity rather than a password, so there is no graph credential to leak or rotate.

Vector search — OpenSearch Serverless

Holds passage embeddings for similarity search, and would also provide keyword search. Two stores rather than one is a deliberate consequence: the reference architecture from AWS reached the same conclusion, because the graph database has no full-text search of its own.

Two infrastructure notes recorded during the build, both non-obvious:

  • Access requires two separate grants, not one. An identity policy allowing API access is insufficient on its own; a separate data access policy must name the principal. Without it you get a permission error with no indication that a second half is missing. It lives in the app stack rather than the data stack because it names the application's task role, and the tool attaches policy to the stack owning the role.
  • Standby replicas are enabled because with a minimum capacity of zero there is no floor to double, so an idle collection bills nothing either way and the redundancy is free.
  • The collection is reached over public DNS, not a private endpoint, and that is a constraint of this collection generation rather than a preference. A next-generation collection's hostname sits in a domain the private zone attached by the service's VPC endpoint does not cover, so inside the network it resolves to a public address and the network policy refuses the request as coming from the internet. There is no configuration in which the private endpoint works for it. The alternative is the older collection type, which resolves privately but carries a two-unit capacity floor, roughly $350 a month while idle against scaling to zero.
What that costs, stated plainly

One layer fewer than the design intended. Reaching the collection over the public internet is not the same as being able to read it: the data access policy still names a single principal, every request is signed, indexes are one per firm so a scoping mistake fails closed rather than open, and the interactive dashboard is deliberately absent from the policy so there is no browsable read path to privileged text.

But defence in depth means not relying on any single one of those, and this removed the outermost. It should be revisited if the private zone ever covers the newer domain, and it is the reason the failure took five attempts to diagnose: the refusal arrives as a bare authentication error with no body, which sends you to look at credentials and permissions that were correct the whole time.

Embeddings are written here, one index per tenant, named so that a mistake fails closed with "index not found" rather than returning another firm's documents. The matter wall is applied as a pre-filter inside the k-NN query rather than afterwards: post-filtering returns fewer than the requested number of results whenever a screen bites, and a lawyer reads that shortfall as "nothing relevant" instead of "you cannot see it". Similarity is cosine, matching the in-process reference store, so a local result and a deployed one rank the same way.

Models — Amazon Bedrock

Provides the extraction model, the query model, the enrichment model and the embedding model. All four are governance settings rather than constants, so a deprecation is a settings change rather than a release. See Governance settings.

One small operational detail worth recording because it cost time: the newest models reject a temperature parameter outright. Sending a temperature of zero in the interest of reproducibility failed every extraction with a validation error, which is worse than not pinning it. The parameter is omitted by default.

One image, two entry points

The agent tool server runs the same container image as the API, entered at a different module. That is the important decision in that stack, and the reason is a governance one rather than an operational one.

A tool that answered a question differently from the equivalent web request would mean two implementations of governance — and the tool implementation is the one nobody audits. Same image, same scoping module, same vocabulary gate. The managed runtime validates the caller's token before any of this code runs, so a tool call arrives carrying the same verified firm identity a web request does. There is no service-account path into the graph.

Authorisation

Sign-in is handled by a managed user directory; the firm identity is a claim in the verified token and is never read from a request parameter. The identifier that appears in a URL path exists for routing and readability — it is validated against the token claim, and a mismatch is refused.

Matter-level access uses a policy language whose defining property, for this system, is that a forbid overrides any permit. That is what makes an ethical wall undefeatable by a broad role. See why a denial beats a permission.

One infrastructure trap worth recording. The tool runtime and the application share a single role trusted by two service principals, rather than one assuming the other. Assumption would require a trust relationship pointing back from the tool stack to the application stack, which is a circular dependency between stacks. A related trap: the deployment tool attaches policy statements to whichever stack owns the role, so grants written in the tool stack silently emit into the application stack's template and deploying the tool stack alone would not apply them. They are written in the application stack for that reason.

Not built yet

No authorisation policies have been authored. The authorisation context has the right shape — a list of permitted matters and a list of forbidden ones — and the deny-wins logic is implemented and tested. The policies that would populate it do not exist, and whether the managed policy service supports the override pattern the design depends on is recorded as an open question.

The availability zone constraint

Do not simplify the network stack

The agent runtime supports only a subset of availability zones in the target region. The vector search service's private endpoint supports a different subset. The virtual network must be pinned to the intersection of the two.

Zone names are shuffled per account, so the intersection can only be resolved against the account being deployed to — which is why the zone list is currently unset, and is one of two things that must be resolved before any deployment. Left unset, the deployment tool picks the first two zones, which may not be in the intersection. The symptom is a deployment that breaks for a reason with no obvious connection to networking.

The second pre-deployment blocker is that the user directory is currently configured to be destroyed when its stack is removed. That must become retain before the first real firm is onboarded: there is no import path back for a deleted user directory.

Cost shape

Roughly $135–190 per month at idle. Two things dominate, and the larger one is surprising:

  • The graph database bills continuously with no scale-to-zero — free for an initial allowance of instance-hours, then around $50 a month.
  • The nine private network endpoints cost around $65 a month, which is more than the application containers. They are the first thing to remove from a throwaway environment, at the cost of routing that traffic through the outbound gateway instead.

Local development

Local development uses Neo4j in a container in place of the managed graph database. This works because both speak openCypher over the same protocol, so the same client code runs against either without a compatibility layer.

The compose file defines the graph database, a vector search container behind an optional profile, the API, the tool server behind another profile, and the browser application.

docker-compose up -d neo4j

ENVIRONMENT=local AUTH_DEV_BYPASS_TENANT=dev-tenant \
  GRAPH_URI=bolt://localhost:7687 GRAPH_USER=neo4j GRAPH_PASSWORD=... \
  .venv/bin/python -m uvicorn src.api.app:app --port 8010

The development authentication bypass is gated twice — once when configuration is validated, and again at request time — because a bypass that is only checked at startup is a bypass that survives a configuration change.

Two differences from deployment are worth knowing. Constraints and indexes are applied locally and skipped when deployed, as described above. And the port the container listens on is fixed at 8000 because the agent runtime's protocol contract requires it, so the API uses the same port and local matches deployed.

What running it locally actually proved

A local run against a real filing confirmed several of the guarantees on these pages end to end, and it is worth recording which, because a passing unit test and a working system are different claims:

  • Provenance was byte-exact against the original document.
  • Re-ingesting identical bytes changed nothing — content-addressed identifiers collapsed the duplicate.
  • A cross-firm read returned 404, and staging another firm's fact was refused at the contract boundary rather than at the web layer.
  • A walled user saw a subset, and a direct probe by identifier was refused with a message that did not reveal a wall exists.
  • The cap/floor invariant held over HTTP — raising the floor succeeded; lowering it into the model cap returned an error with the explanation.
  • The kill switch refused an ungoverned question with a message written for a lawyer.
Why the local run mattered

Two bugs surfaced in that run that several hundred green unit tests had not. Both came from a whitespace pattern matching newlines, so a run of title-case words walked across a line break: a plaintiff name absorbed the entire court header above it, and a defendant name absorbed the docket line below it.

Either would fork the party entity so it never matched the same party elsewhere in the graph — which makes a conflict check under-report silently. That is the failure this whole system is built to prevent, arriving through a line-wrapping detail. Both are fixed, with regression tests covering realistic multi-line filings and asserting that entity identifiers stay stable across layouts.

The code those bugs lived in has since been deleted along with the pattern-matching extractor. The lesson has not: entity identity is the thing to test hardest, because getting it wrong produces a reassuring answer.

State of the build

Around 6,000 lines of Python, six infrastructure stacks that synthesise cleanly, and twelve interface pages. The test suite runs 1,168 tests and is green.

The largest functional gaps, repeated here in one place:

  • No query executor wired to the metric path, so governed metrics compile SQL that is never run. The Athena executor itself exists and is tested.
  • No model-backed SQL generator. Nothing turns a question into SQL, so a question no approved metric matches is answered from the graph, the passages and the table definitions, or not at all. A generator is planned inside tier 3, checked against the parsed syntax tree before it runs; it is not built.
  • No authorisation policies authored.
  • Ingestion and live progress events both depend on there being a single task.
  • Nothing deployed. The infrastructure has been synthesised and never applied.
